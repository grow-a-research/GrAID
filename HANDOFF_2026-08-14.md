## The original problem

Reported symptom: clicking "process" on a submission caused a visible CPU spike
on the local machine, Vast's GPU/CPU utilization stayed low, and grading one
essay took roughly 20-30 seconds.

First finding: **grading and OCR are separate systems, and only one touches the
GPU.** `grade_essay()` calls Groq's cloud API (`llama-3.3-70b-versatile`) —
network-bound, not local/GPU compute. The GPU work is entirely in OCR: Surya
(line detection) + Qwen2.5-VL-7B-Instruct, 8-bit quantized, running on a rented
Vast.ai GPU that the local backend delegates to over HTTP (`REMOTE_OCR_URL`).
The reported 20-30s was therefore overwhelmingly OCR time, not grading time.

## Fixes made, in order, with before/after measurements

### 1. Qwen batching + single-GPU pinning (`ocr_pipeline.py`)

- **Before:** `qwen_ocr_lines()` called `model.generate()` once per detected
  handwriting line, in a Python loop — no batching, each call paying fixed VLM
  overhead regardless of line count. `device_map="auto"` also split the model
  across both GPUs on the original 2x RTX 5060 Ti instance, even though the
  model only needs ~8-10GB in 8-bit and fits on one card — adding PCIe
  cross-GPU transfer overhead (no NVLink on that hardware) for no benefit.
- **Fix:** batch up to 8 line-crops per `generate()` call (chunked via
  `QWEN_OCR_BATCH_SIZE`), with left-padding on the tokenizer (required for
  correct batched causal-LM generation — right-padding would produce garbage
  for the padded rows). `device_map={"": 0}` pins the model to one GPU.
- **Measured:** user-reported essay processing time dropped from ~25s to ~19s
  after this change (first round-trip user test, before finer-grained timing
  existed).

### 2. ArUco alignment: detect on a downscaled copy (`ocr_alignment.py`)

- **Before:** marker detection ran `fastNlMeansDenoisingColored` (a
  notoriously expensive OpenCV function) on the **full-resolution** original
  phone photo before ArUco detection — paying for precision the detector
  doesn't need. Measured at **5.37s** on a real test submission (Carlos's
  essay, submission 9).
- **Fix:** detect on a copy downscaled to a 1600px max dimension, then scale
  the found marker corners back up to original-image coordinates before
  computing the homography. The actual perspective warp still runs on
  full-resolution pixels — OCR input quality unaffected.
- **Measured:** same alignment step dropped to **1.32s** on the same
  submission — a ~4x speedup, confirmed via before/after log timestamps.

### 3. Logging was silently broken (`main.py`)

- **Before:** nothing in the project called `logging.basicConfig()`. Every
  `logger.info()` call across the whole app — including all the new timing
  instrumentation below — had no attached handler and printed nowhere.
- **Fix:** added `logging.basicConfig(level=logging.INFO, ...)` at the top of
  `main.py`.

### 4. Timing instrumentation added

Added `[Timing]` log lines at every pipeline stage so the breakdown could be
measured instead of guessed:
- **Local** (`job_queue.py`, `routers/api_v1.py`): align/warp time, remote-OCR
  round-trip time, Groq correction-call time, Groq grading-call time.
- **Vast** (`ocr_pipeline.py`, `vast_ocr_server.py`): Surya detection time,
  Qwen transcription time (with line count), total server-side `/ocr`
  handling time.

This is what made every measurement below possible.

### 5. Bug: over-aggressive paragraph merging (`ai_grader.py`)

- **Found:** the Groq OCR-correction step (`correct_ocr_text`, layout cleanup
  only, per a 2026-08-06 fix) was merging multiple **complete, distinct**
  sentences into one run-on paragraph — its "merge fragmented lines" rule was
  meant only for genuine physical line-wraps, but the model was applying it
  whenever lines seemed topically related.
- **Fix:** tightened the rule to a punctuation-based test (only merge a line
  into the next when it lacks sentence-ending punctuation) with a concrete
  example.

### 6. Bug introduced, then fixed same session: self-narration leak

- **Root cause:** the counter-example added in fix #5 used the phrasing
  *"...must stay separate, NOT **become**..."* — the model latched onto that
  word and started literally narrating a before/after transformation into its
  actual output.
- **Found via:** direct SQLite query against submission 9 / answer 93 — the
  stored `ocr_text` was `[raw text]...becomes...[near-duplicate text]`, length
  367→746 chars, and had been graded as-is (score 7.0 against garbled double
  text, instead of the correct 5.0 against the real answer).
- **Fix, three parts:**
  1. Reworded the example to state the two lines directly instead of
     narrating a transformation.
  2. Added an explicit rule forbidding before/after echoing and words like
     "becomes."
  3. **Added a structural, wording-independent safety check** to
     `_looks_like_runaway_correction()`: if the raw OCR text appears as a
     literal substring inside a meaningfully-longer "corrected" result,
     reject it and fall back to raw text — catches this failure *shape*
     regardless of what phrase the model uses next time, rather than
     keyword-matching specific phrasings (which is how this slipped through
     the first time).
- **Verified:** restarted, re-ran OCR+Grade on submission 9, re-queried the
  DB — clean single copy of the text, correct score (5.0) restored.

### 7. Bug: accidental local model loading (`ocr_pipeline.py`, `vast_ocr_server.py`)

- **Found:** leaving `REMOTE_OCR_URL` blank in a fresh terminal caused the
  local backend to load the full Surya+Qwen stack onto the laptop's own weak
  GPU (RTX 3050 Laptop) instead of gracefully disabling OCR — contradicting
  `run_graid.ps1`'s own (previously inaccurate) "OCR endpoints will return
  503" message. Root cause: `load_models()` unconditionally fell through to a
  local-CUDA-load branch whenever `REMOTE_OCR_URL` was empty, and that
  function is shared between the main app and `vast_ocr_server.py` (which
  legitimately *always* wants local loading, since it clears
  `REMOTE_OCR_URL` before calling it).
- **Fix:** added a `force_local` parameter. `vast_ocr_server.py` now passes
  `force_local=True` explicitly (unchanged behavior — it always loads
  locally). The main app's call (`force_local=False` default) now correctly
  skips loading and leaves OCR endpoints returning 503 when no remote URL is
  configured, instead of silently loading onto whatever local GPU exists.

### 8. Old Vast instance died; new one rented

- The original instance (46802476, 2x RTX 5060 Ti, `158.181.52.18:43240`,
  $0.361/hr) went into "scheduling" mode and became inaccessible.
- New instance rented: **47646208**, 1x RTX 5060 Ti, `85.10.218.46:35102`
  (internal port 10100), **$0.199/hr**. Confirmed adequate — actually a better
  fit than the old 2-GPU instance, since the single-GPU pin from fix #1 means
  the second GPU on the old rental was already going unused for this
  workload. `VAST_AI_DEMO_CHECKLIST.md` updated with the new instance's real
  ID/IP/port/price.

### 9. Dropped a wasted network payload (`ocr_pipeline.py`, `vast_ocr_server.py`, `job_queue.py`, `routers/api_v1.py`)

- **Found:** every grading-pipeline OCR call requested a full annotated debug
  image back from Vast (PNG, base64-encoded — ~33% size inflation from the
  encoding alone) and immediately discarded it (`_ = ...`). Only the
  standalone OCR Tool debug page actually displays that image; all six real
  grading call sites never used it.
- **Fix:** added an `include_boxed_image` flag threaded from
  `run_ocr_pipeline()` through the HTTP request to Vast. All six grading call
  sites now pass `include_boxed_image=False`; the debug page is unaffected
  (defaults to `True`).
- **Measured impact: small.** Network overhead before: 6.19s / 6.05s (two
  tests). After: 5.86s. A real but minor ~0.2-0.3s improvement — most of the
  network cost was never this payload.

## Final measured breakdown (real test runs, not estimates)

| Run | Align | Remote OCR round-trip (local) | Vast server-side total | → Network overhead | Surya | Qwen | Groq correction | Groq grading |
|---|---|---|---|---|---|---|---|---|
| Sub 9, pre-alignment-fix | 5.37s | — (13.35s combined w/ correction) | — | — | — | — | — | 1.14s |
| Sub 9, post-alignment-fix | **1.32s** | — (13.48s combined) | — | — | — | — | — | ~1.3s |
| Sub 11, cold (new instance) | 2.42s | 22.65s | 16.46s | **6.19s** | 2.01s | 12.46s (4 lines, ~3.1s/line) | 1.16s | 1.30s |
| Sub 12, warm | — | 15.96s | 9.91s | **6.05s** | 0.46s | 7.45s (14 lines, ~0.53s/line) | 0.81s | 1.15s |
| Sub 11, warm + no boxed-image | 2.66s | 20.83s | 14.97s | **5.86s** | 1.58s | 11.38s (7 lines) | 0.97s | 1.11s |

**What this data says, clearly:**
- Alignment fix: consistently effective, ~4x (5.37s → 1.3-2.7s depending on
  scan).
- **Network overhead is real and structural, not a warm-up artifact** — it
  sat at 5.86-6.19s across cold runs, warm runs, and before/after the
  boxed-image fix. It's the inherent cost of sending an image to a rented GPU
  over the internet and getting text back — nothing left to trim there
  without a bigger architecture change.
- **Qwen transcription dominates whichever run you look at**, and is highly
  sensitive to cold-vs-warm state: ~3.1s/line on the first request after
  model load, dropping to ~0.53s/line once warm — a ~6x difference. The
  batching + single-GPU fixes are working correctly; first-request-after-
  restart just pays a real, one-time CUDA/cuDNN warmup cost.
- Surya detection: fast either way (0.46-2.01s).
- Groq calls (correction + grading): consistently fast, 0.8-1.3s each, never
  a bottleneck at any point in this investigation.

**Net result:** total per-essay time is now roughly in the high-teens to
high-20s seconds depending on essay length (more lines → more Qwen time), a
real but not dramatic drop from the original 20-30s report — because the
single largest remaining cost (network round-trip, and Qwen's cold-state
sensitivity) is largely irreducible within the current "laptop backend +
rented GPU for OCR" architecture. Genuine further reduction would mean
collocating the whole backend on Vast (eliminates the network hop) — explored
and deliberately **not** pursued right now: it was already tried once (full
`FORCE_LOCAL_OCR` test) and found to be slow in practice, and moving the
system's data (SQLite DB + submission files) onto rented, potentially
ephemeral compute is a real risk this close to the defense.

## What's worth citing in the paper

This entire investigation is legitimate Methodology/Limitations content: a
measured, systematic breakdown of a remote-inference architecture's latency
sources, with hypotheses tested and ruled out one at a time (cold-start vs.
structural network cost; debug-payload waste vs. genuine transfer cost). If
asked "why does grading take this long," there's now a real, evidence-backed
answer instead of a guess: local GPU can't run the VLM at usable speed/memory,
so OCR delegates to rented compute; the ~6s network round-trip is a measured,
inherent cost of that delegation, not a bug — confirmed by ruling out cold
start and payload size as the explanation.
