## Fixed and verified working

### 1. Structured grading truncation (`ai_grader.py:427`)
`grade_answer_structured`'s 900-token output cap (for a 3-criterion rubric)
didn't leave room for both gpt-oss-120b's reasoning *and* the JSON answer, so
2 of 3 criteria were getting cut off and zero-filled — confirmed on a real
record (submission 12/question 45, scored 9.0/25 instead of correctly).
**Fix:** raised the cap to `min(4096, 1000 + 400 × criteria)`, left
`reasoning_effort` at Groq's default (explicit user choice — preserve grading
quality over saving tokens). **Verified:** two fresh real submissions graded
correctly afterward, all 3 criteria populated (18.5/25, 19.5/25).

### 2. Upload state leaking across submissions (`frontend/src/pages/SubmissionsPage.jsx:118-129`)
Picking a file (or camera photo) only stages it locally until "Upload" is
clicked; that staged state wasn't cleared when switching submissions, so it
visually "leaked" onto whichever submission you opened next, and looked like
"uploaded files disappearing" if you navigated away before actually
uploading. **Fix:** the effect that runs on submission-switch now also resets
`uploadFile`, `captured`, and camera state (stopping any live stream).
**Verified live**, in-browser, before and after the fix.

### 3. Wrong paper attached to submission #12
Labeled "Jan Paul Cabrera" but the actual scanned photo was Carlos
Espiritu's paper (duplicate of submission #10). **Fix:** deleted the file,
the stale empty answer row, and an orphaned `aligned_p1.png` artifact (the
file-delete API endpoint doesn't clean that up itself); reset submission
status to `draft`. **Still needed:** the user has to upload Jan Paul
Cabrera's actual paper — nothing more to do in code here.

## Fixed in code, but NOT yet confirmed working — this is where we left off

### 4. OCR-correction word-dropping — diagnosed only, on hold
The Groq text-cleanup step (`correct_ocr_text`, `ai_grader.py`) sometimes
drops real words ("a", "In", "are") despite being told not to. Reproduced
live once, but it's intermittent — a repeat test with similar input didn't
drop words, instead violated a *different* rule (splitting every sentence
onto its own line). Conclusion: probabilistic model-compliance issue, not a
deterministic code bug. **Proposed, not built:** a word-preservation guard
parallel to the existing `_looks_like_runaway_correction()` at
`ai_grader.py:525` — compare word sets raw vs. corrected, fall back to raw
text if real words go missing. **User said hold off.** Repro script:
`scratch_test_ocr_correction.py` in repo root.

### 5. ArUco/QR top-right corner clipping — diagnosed only, on hold
Only 3 ArUco markers exist (TL/BL/BR, see `pdf_generator.py:60-65`) — the QR
code occupies the unanchored 4th (TR) corner, so `detect_and_warp()`'s
homography is least accurate there, and `warpPerspective`'s output canvas has
no safety margin (`ocr_alignment.py:316-321`), so the QR gets clipped in the
"Aligned scan" preview. **Confirmed does NOT affect grading** — answer
regions sit in the well-anchored content area, not that corner. **Proposed,
not built:** pad the warp canvas. **User said hold off** — cosmetic only.

### 6. Empty OCR text / silent grading failure — code fix applied, verification INCOMPLETE ⚠️
**Original finding:** 2 of 4 test submissions came back with completely
empty `ocr_text` despite the crop being provably legible (visually confirmed
by reproducing the exact crop sent to OCR) — the code was unconditionally
marking these `status="done"` with no error surfaced, so a submission could
silently never get graded.

**Fix applied in two places** (the codebase has two independent, duplicated
implementations of this OCR loop):
- `job_queue.py:225-254` (background "Process all pending" queue path)
- `routers/api_v1.py:778-808` (single "Process paper" button path — the one
  actually exercised by manual testing)

Both now: if OCR returns empty text, retry the remote call once (this was
diagnosed as a transient remote-server hiccup, not a bad crop). If still
empty after the retry, mark the answer `needs_review` instead of `done`, so
it's visibly flagged instead of silently looking complete.

**What happened when we tried to verify it, in order:**
1. Backend restarted by the user (confirmed via new process ID, 4444 → 9036).
2. Clicked "Re-process" on submission #10 (Carlos, the clean/correct paper)
   → **"Internal Server Error"** in the browser. Traceback never captured —
   my sandboxed shell doesn't have the live server's `REMOTE_OCR_URL`/
   `GROQ_API_KEY` env vars, so standalone repro attempts hit a different,
   unrelated 503 instead of the real error. **Still needed: the user pasting
   the actual traceback from their server's terminal window.**
3. User ran a fresh independent test: uploaded a new photo to submission #9
   (Ryan Calma) and processed it. Result (confirmed via read-only DB query):
   `ocr_text` came back empty **again**, even after the retry — but this
   time correctly marked `needs_review` (the visibility half of the fix is
   confirmed working). The photo itself was checked (viewed the saved
   `aligned_p1.png`, read-only) and is completely legible — same quality as
   every submission that worked earlier in the session.

**Where this leaves the diagnosis:** three separate legible photos have now
failed OCR (submissions 10, 12 originally, and now a fresh upload on 9), and
the retry didn't recover it on the most recent one. What looked like an
occasional transient blip when it was 2-of-4 now looks more like the remote
OCR service (the Vast.ai instance) may be down, degraded, or otherwise
unhealthy in a more persistent way — not just flaky under load. **This is
unconfirmed.** I asked the user for permission to check the remote OCR
server's `/health` endpoint (or for them to check the Vast.ai dashboard
directly) and the session ended before getting an answer.
