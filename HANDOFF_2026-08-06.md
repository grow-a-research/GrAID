## For the paper — use this content directly

### 1. Qwen grammar-normalization limitation (cite in Limitations)

Confirmed, reproducible finding: Qwen2.5-VL-7B-Instruct (8-bit quantized)
silently "corrects" grammatically non-standard handwriting toward its
learned language prior — e.g. transcribing a handwritten singular noun
("solve problem") as the grammatically-expected plural ("solve problems") —
**even with an explicit anti-correction prompt containing that exact
counter-example.** Isolated via `SKIP_OCR_CORRECTION=1` (bypassing the
separate Groq cleanup step) to prove the error originates in Qwen's
transcription itself, not downstream correction. A follow-up prompt
strengthening attempt did not resolve it.

Draft Limitations paragraph (already written, ready to adapt):

> The system's handwriting transcription stage relies on Qwen2.5-VL-7B-Instruct
> (8-bit quantized) as a pretrained vision-language model. While the
> transcription prompt explicitly instructs the model to reproduce text
> verbatim — including grammatical errors — testing revealed that the model
> occasionally normalizes clearly non-standard grammar toward its learned
> language prior (e.g., silently pluralizing a singular noun to match expected
> subject-verb agreement) even when the handwritten evidence is unambiguous.
> This reflects a known limitation of VLMs generally: they remain language
> models at their core, and explicit instruction-following does not fully
> suppress patterns learned during pretraining, particularly in smaller,
> quantized model variants with less capacity to override strong internal
> priors. Fine-tuning or training a custom model to eliminate this behavior
> was considered but judged out of scope: it would require a purpose-built
> labeled dataset of handwriting-to-verbatim-transcription pairs preserving
> deliberate errors — no such dataset exists for this domain, and constructing
> one is a substantial data-collection undertaking in itself — plus dedicated
> training compute beyond what this thesis's system-integration scope calls
> for. This is consistent with the study's framing as an applied AI-assisted
> grading *system* built on pretrained foundation models, rather than a
> model-development contribution.

Defense soundbite if a panelist asks "why didn't you fine-tune":

> "We did consider that, but fine-tuning needs labeled training data we
> don't have — handwriting images paired with verbatim transcriptions of
> deliberate errors — and building that dataset is its own research project.
> Our contribution is the integrated grading system and its evaluation, not
> a new OCR model, so we scoped that as future work rather than pulling
> months of dataset construction into this thesis."

### 2. Print/photo-quality dependency (already a limitation category — reinforced)

Diagnosed a real ArUco alignment failure down to pixel level: a marker
printed at drastically lower contrast than its siblings on one physical test
sheet (confirmed via direct crop inspection — not a code bug, not a photo
lighting/angle issue, not orientation; ruled out via a fresh, well-lit
retake that still failed identically). This is concrete evidence for the
existing "input-image dependency" / "pretrained-model dependency" limitation
categories — worth a sentence noting alignment reliability is sensitive to
physical print/scan quality, independent of software.

### 3. Trust & Transparency / RQ4 flagging metric — confirm you understand the mechanics before writing about it

`GET /exams/{id}/flagstats` computes Precision/Recall for the auto-flagging
system:
- **TP** = flags with `review_decision = 'confirmed_error'`
- **FP** = flags with `review_decision = 'false_positive'`
- **TN** = flag rows with `review_decision = 'verified'`
- **FN** = *unflagged* graded answers where `teacher_score` differs from
  `ai_score` by ≥ max(0.5, 10% of max_points) — a proxy for "the system
  missed a real error"

Tested live with one real answer (AI scored 12/20, teacher override 15,
marked "verified" without an actual triggered flag) → correctly produced
FN=1, Recall=0%, demonstrating the metric works. Worth noting in methodology:
`review_decision='verified'` is deliberately excluded from the "flagged"
count (it's not a real flag), and FN is a *heuristic* (score-divergence
proxy), not ground truth — relevant if a panelist asks how missed errors are
actually detected without a human labeling every single answer.

## Technical summary — what changed today (for your own reference, not paper content)

Ten commits landed today (`bda38fa`..`4ae9a91`), fixing, in order:

1. **Server-wide freeze during processing** — two FastAPI routes were
   `async def` but ran the full OCR/grading pipeline synchronously inline,
   blocking the single event loop for every user, every page, for the whole
   processing duration. Fixed → plain `def` (FastAPI auto-threads those).
2. **OCR detecting nothing on real scans** — a later commit's sharpness gate
   + content-trim regressed detection to zero. Reverted `ocr_pipeline.py` /
   `ocr_alignment.py` to the last known-good version.
3. **Submissions OCR quality worse than the standalone OCR Tool** — the
   alignment pipeline was stacking denoise+CLAHE+resample+CLAHE+sharpen onto
   every crop before Qwen ever saw it. Fixed: detect markers on a throwaway
   processed copy, but warp/crop the *original* unedited pixels.
4. **Groq correction step silently fixing spelling/grammar** — over broad
   prompt let it "improve" content, skewing rubric-graded answers. Narrowed
   to pure layout cleanup (merge fragmented lines, strip printed question
   text) with an explicit content-preservation rule.
5. **Wrong grades from the fallback OCR path** — when alignment fails,
   answers get `question_id=None` and previously graded against hardcoded
   generic placeholders (`max_points=10.0`) instead of the exam's real
   rubric. Fixed: auto-associate with the exam's one gradable question when
   unambiguous; flag `needs_review` when genuinely ambiguous. Applied to all
   three grading paths (single, bulk, background queue).
6. **EXIF photo orientation never applied** — phone photos store raw sensor
   orientation + a rotation tag; the pipeline was processing raw/unrotated
   pixels. Fixed with `ImageOps.exif_transpose()` everywhere an uploaded
   photo is loaded.
7. **DB connection pool exhaustion during bulk processing** — bulk endpoint
   held one connection for the entire multi-minute batch, starving other
   requests. Fixed: short-lived per-submission session, closed after each one.
8. **Duplicate concurrent bulk-process runs** — no server-side guard, so
   navigating away and back (or a second groupmate) could kick off an
   overlapping batch reprocessing the same submissions. Added an in-memory
   lock + a status endpoint driving a real (not per-tab) loading indicator.
9. **Orphaned answers surviving file deletion** — deleting a submission file
   left its `SubmissionAnswer` (and flag) behind, causing stale OCR/grading
   results to resurface — including a real "phantom page 2" that inflated a
   score to 26/20. Fixed going forward; one pre-existing orphan cleaned up
   directly in the DB this session.
